# 电脑与手机加载卡顿：诊断与解决方案

日期：2026-09-28。基线：电脑 `6589a3b`；手机/手表 `d4912fb`。

## 1. 结论

当前至少有三类问题，不能用一个“加载动画优化”解决：

1. **电脑人物统计存在实际慢 SQL。** 总结与关系、人物与声纹共用人物接口，均被它拖住。正式服务的人物接口本次 50 秒仍未返回；其他并发读取能正常返回。
2. **页面把互不依赖的数据绑在同一个加载状态中。** 快数据也要等慢数据；刷新时已有内容被隐藏。审核还重复读取声纹候选。
3. **手机长录音详情一次布局所有转写。** 点击详情本身没有请求电脑，但会创建大量行；全量缓存刷新、同步文件扫描和全局状态通知也会增加主线程工作量。

优先顺序：人物统计查询 → 手机详情列表虚拟化 → 电脑分区加载/缓存 → 两端按需读取和增量刷新 → 审核及候选查询优化。

本次为诊断与方案：未修改业务源码、正式数据库或设备安装。索引实验仅在内存数据库副本上执行。

## 2. 测量范围与证据

正式数据库以 SQLite `mode=ro` 打开；查询实验设置 25 秒上限。另对当前运行的本机 8765 服务做只读业务接口请求，正常恢复桌面会话，单个请求上限 50 秒。数据库副本使用 SQLite backup API 创建到内存。

当前规模：23 条会话记录（列表返回 21 条有效记录）、8,143 条转写（8,136 条 active）、9 人、3,875 个声纹簇、3,886 条说话人轨道、173 个声纹原型、4,748 条标注事实。单会话最多 1,673 条 active 转写。

### 实际测量

| 路径 | 本次结果 | 含义 |
|---|---:|---|
| HTTP `/api/v3/persons` | 50 秒客户端超时 | 没有拿到成功响应；不是说接口恰好 50 秒完成 |
| 人物 `summary_counts()` 首条 SQL | 超过 25 秒后中止 | 已定位到具体慢查询 |
| HTTP 日报列表 | 22 ms，约 67 KB | 总结页的等待不等于日报生成或读取慢 |
| HTTP 审核列表 | 415 ms，返回 0 项 | 当前空队列下未复现数十秒；不能代表有大量审核时的性能 |
| HTTP 待审核声纹候选 | 298 ms，约 36 KB | 审核页面随后又请求这份数据 |
| 仓储录音列表 | 1 ms，1 条 SQL | 当前主要瓶颈不在列表本身 |
| 仓储最长转写会话详情 | 84 ms，9 条 SQL；序列化约 8.36 MB | SQL 不算很慢，返回体和客户端处理负担大 |
| 仓储声纹候选 | 66 ms，113 条 SQL，28 项 | 存在逐项补查询；数量增长后会放大 |
| 仓储审核列表 | 137 ms，118 条 SQL，0 项 | 即使最终没有审核项，也会执行大量准备查询 |
| 仓储概览 / 数据健康 | 约 2.5 ms / 2.5 ms | 本次没有发现明显读取瓶颈 |

以上为单次诊断值，不是 P95，不应混用 HTTP 与仓储耗时相减来推断某一层的固定成本。HTTP 耗时包括应用逻辑、序列化和服务当时的负载。

手机已连接且应用运行，但本次没有取得可靠的点击到首帧、长帧或掉帧 trace。因此手机的具体毫秒数尚未测定，下文区分代码确认的工作量和需要真机量化的影响。

证据输出（忽略的 outputs 目录，不进入业务提交）：

- `outputs/page-load-profile-20260928.json`：仓储耗时、SQL 数和慢语句。
- `outputs/page-http-profile-20260928.json`：实际 HTTP 测量。
- `outputs/page-index-experiment-20260928.json`：内存副本索引前后对比及结果一致性。
- `outputs/profile_page_reads.py`、`profile_page_http.py`、`profile_page_index.py`：本轮诊断脚本。

## 3. 电脑：明确根因

### 3.1 人物统计反复全表扫描

入口：`application/people_prototypes.py:list_people()` 不仅查询人物，还调用 `person_memories.summary_counts()`。

慢点：`adapters/sqlite/person_memory_repository_queries.py:68`。该查询将人物、记忆、人物关联、声纹成员和会话连在一起，再对每条轨道执行 `EXISTS (SELECT ... FROM utterances WHERE speaker_track_id=...)`。当前转写表只有主键、run/ordinal 唯一约束，以及会话/时间和会话/身份索引，没有按说话人轨道查 active 转写的索引。

`EXPLAIN QUERY PLAN` 明确出现 `CORRELATED SCALAR SUBQUERY` 下的 `SCAN u`。记忆和轨道的一对多连接还会放大中间行数；即使人物只有 9 个，也会重复访问大量转写。

**隔离验证：同一份内存数据库副本，相同查询，相同 9 行结果。**

| 版本 | 查询耗时 |
|---|---:|
| 原查询、原索引 | 7,860 ms |
| 仅增加 active 转写的轨道索引 | 77.9 ms |

约 101 倍改善。内存副本和正式磁盘/服务环境不同，不能把 77.9 ms 当作上线承诺；它验证了索引缺失确实是瓶颈。

建议先新增迁移中的部分索引：

```sql
CREATE INDEX idx_utterances_active_speaker_track
ON utterances(speaker_track_id)
WHERE status = 'active';
```

随后把“人物记忆数”和“人物会话数”分别聚合后连接，避免记忆数 × 轨道数的中间结果。把事件 JSON 每事件解析一次，再统计人物引用，替换当前按每个人重新解析全部事件的循环。保持原来的声音类型、人物确认、失效标注过滤条件及去重语义。

### 3.2 一个慢接口阻塞整页

- `views/InsightsView.vue:19`：日报、关系、完整人物列表放在同一个 `Promise.all`。日报已经返回也不能显示。
- `views/PeopleView.vue:14`：声纹簇、人物、录音、全部状态的候选四项一起等待。进入“人物”模式也加载声纹相关数据。
- 人物页 `watchEffect` 又会自动选择人物和声纹簇，存在隐藏模式也加载详情的额外工作。

解决：按可见区域拆分查询和加载状态。日报先显示，人物选择器单独加载；人物模式与声纹模式按需取数。人物选择器采用轻量 `id/name` 数据，不强制依赖统计数据。当前手机标注已有 `people_choices()`，可以在保留权限和契约校验的前提下复用查询逻辑。

### 3.3 缓存没有保留已显示内容

`core/query.ts` 只有 30 秒页面级缓存。超过 30 秒重新进入页面时，初始数据为空；刷新也把 `loading` 置为 true。`components/PageState.vue:15` 在 loading 时隐藏整个内容插槽。

还没有共享的在途请求去重、组件退出取消和防止旧响应覆盖新响应的机制。不同页面分别请求人物接口，不能共享一次进行中的人物查询。`core/api.ts:74` 的 fetch 没有应用级超时，长查询会一直表现为加载。

解决：

- 缓存命中时立即展示，过期后后台刷新；区分初次加载与刷新。
- 刷新只显示局部状态，不卸载原列表，不重置滚动位置和选中项。
- 按资源和参数共享缓存、在途 Promise；最后一个订阅者退出后取消请求。
- 版本/请求序号防止较旧响应覆盖新选择。
- 只读请求设置明确超时和可重试状态；长时间生成任务使用任务状态，不能套同一个短超时。
- 人工审核、标注、人物修改成功后精确失效关联缓存，不能为了速度展示已失效的判断。

## 4. 审核与其他电脑页面

### 4.1 审核：重复读取与串行等待

`views/ReviewsView.vue:34` 先等待审核列表，再请求声纹候选和必要的提醒候选。但后端 `desktop_review_queries.py:list_reviews()` 生成列表时已经调用了声纹候选查询。

`people_repository_prototypes.py:list_review_candidates()` 先 fetchall 候选，再在 Python 中筛状态、人物和 limit；循环中逐项读取最新审核及人物名。本轮 28 个候选触发 113 条 SQL。最终列表的 `limit=100` 不代表最多扫描 100 条记录。

建议：

1. 把人物名、最新审核和有效候选状态做集合查询；保留授权撤销、失效来源、混声等过滤逻辑。
2. 在数据库完成最终过滤后分页；不能提前随意 LIMIT 导致后面的有效候选丢失。
3. 审核列表只返回卡片必需字段和计数，详情/证据/试听按展开项加载。
4. 复用同次请求中的候选结果，或使列表 DTO 包含已有摘要，避免前端再取整份候选。
5. 对已存在的旧缓存先显示，逐区刷新。

本轮空审核队列的 HTTP 是 415 ms；用户遇到的审核长等待仍需在有审核项、正在同步或后台转写时测量，不能直接归咎于人物统计。

### 4.2 录音详情：概览也下载完整证据

`desktop_recording_queries.py:126` 一次返回 segments、runs、speaker_tracks、utterances、artifacts、backups。当前样本有 1,673 条转写和 1,185 条说话人轨道。压紧 JSON 后，仅 utterance 的 evidence 约 6.20 MB；完整接口使用普通 JSON 序列化约 8.36 MB。

前端虽将时间线初始显示限制为 80 个发言段，仍下载、解析全部转写和证据。不能把显示 limit 当作请求分页。

建议拆为：概览摘要、按 `(start_ms, end_ms, utterance_id)` 游标分页的轻量时间线、单句证据、说话人、运行/备份历史。首屏只依赖摘要和所选标签页；正文保留全文搜索能力，搜索在数据库执行，不能仅搜索已加载页。播放按时间定位，必要时加载附近页。

压缩可减少传输量，但不能替代减少数据量和 JSON 解析成本。

### 4.3 手机审核快照也有额外读取

`interfaces/device_reviews.py:snapshot()` 会读取 pending 候选、审核列表（其中再次读取候选）、confirmed 候选，并为证据读取涉及会话的完整详情。本轮没有执行该服务的正式业务更新，只确认了读取结构。

建议合并同次快照中的候选读取，按候选涉及的 utterance ID/时间范围批量读取证据；避免为几条样本加载整个会话。版本摘要应尽早判断未变更，避免先重建大快照再仅仅丢弃响应。

## 5. 手机：详情卡顿与其他加载问题

### 5.1 详情一次创建全部行

`presentation/phone/PhoneRootPage.ets:139` 的点击流程是选中已有 session 后入栈；`PhoneV3ViewModel.selectSession()` 及 runtime 选择已有录音组，没有等待电脑接口。

`PhoneV3SessionDetailPage.ets:288,470` 使用 `Scroll → Column → ForEach(session.utterances)`。每一行包含多段文本、时间格式化和多个按钮。长录音有近千甚至上千行时，创建/布局工作量随全文增长。

**优先改动：** 用支持可视区惰性创建的 List + LazyForEach 等方案，将头部播放器与列表组织成一个滚动容器，不再外包一个令全部子项布局的 Scroll。只构建可见行和少量预取行。以 utterance ID 维持稳定身份，用 revision/内容更新通知刷新变更行，保留滚动、编辑和播放定位。

首批可从 30–50 行开始，滚动增量加载；这只是初始调优值，不是最终硬限制。批量标注、全文搜索、跳转和“全选”必须针对完整会话，不能因分页而缩减操作范围。

### 5.2 全局刷新读取全部会话转写

`PhoneV3UseCases.ets:162` 的 `loadCached()` 读取全部 recording、processing、utterance、review、reminder 等投影，再重建全部 session。`projectionRows()` 未提供按 session/time 的分页读取。

虽然上一轮已把跨会话重复解析降到“每条投影一次”，仍然是全量工作。`indexSessionUtterances()` 将 evidence 再 stringify；`PhoneV3Utterance` 构造函数又经 annotationFacts、soundKind、personFact、personUncertain 多次解析相同 evidence。异步方法中的这些普通循环和 JSON.parse 仍在当前 JS 执行线程上运行。

建议：

- 会话卡片只带摘要、转写数、状态、最后更新时间；进入详情再按会话取正文。
- 本地投影增加可查询的 session_id、start_ms、状态等列和对应索引，迁移时回填；保留同步所需原始证据。
- 每次收到变更后仅更新涉及的会话/转写页；保留现有增量刷新路径。
- 同一行 evidence 解析一次并派生各 UI 字段；必要的批量解码使用分批任务或后台任务，避免连续占用 UI 线程。
- 完整原始证据可以继续落盘，首屏模型只包含显示所需字段，不删除审计数据。

### 5.3 全量刷新会同步扫文件

`PhoneV3LocalAudioRepository.list()` 每次创建 `PhoneV3RecordingStore`；其构造函数加载清单后继续递归扫描目录，使用 listFileSync/statSync/readTextSync。`refreshSnapshot()` 默认 scanLocal=true，启动、部分操作结束以及本地音频变化后都会走到这里。

这是后台刷新可能让其他页面一起卡的来源，不能说每次点详情都会扫描：直接点击路径没有此调用。

建议复用 runtime 已维护的录音索引，收片/删除时增量更新；目录修复扫描放到异步后台，并合并重复触发。保留损坏索引的恢复路径，但不要每次正常刷新都全盘扫描。

### 5.4 播放状态通知范围过大

`PhoneV3ViewModel.ets:154` 每 500 ms 检查 device 状态。状态确有变化时，dispatch 触发根页 stateRevision 增加，该参数传给详情和多个页面。播放进度变化会扩大 UI 更新范围；具体布局耗时还需要真机 trace。

建议把播放状态独立到播放器组件，转写列表只订阅转写及标注 revision，设备传输状态只通知有关组件。避免每半秒通知全文详情。人物、审核、录音列表等较大 ForEach 同样纳入懒加载和可见页更新检查。

## 6. 实施批次与验收

| 批次 | 改动 | 验收重点 |
|---|---|---|
| 第一批 | 人物统计索引与分开聚合；手机详情虚拟列表 | 人物接口恢复快速返回；上千句详情首屏不全量创建行 |
| 第二批 | 电脑分区加载、共享请求缓存、刷新保留内容；手机播放局部状态 | 慢人物接口不阻挡日报；切页/刷新不清空现有内容；播放不驱动全文重绘 |
| 第三批 | 两端详情分页与轻量 DTO；手机投影索引、解析一次、文件增量索引 | 首屏开销随页大小增长，不随全部历史转写增长 |
| 第四批 | 审核集合查询、候选与证据复用；列表分页补齐 | SQL 数不再按每个候选增加；大量审核时仍可用 |

建议目标（待修复后实测，不是当前已达到）：

- 电脑常用只读首屏接口暖态 P95 < 300 ms；人物列表和审核复杂接口 P95 < 500 ms。
- 缓存返回页面首个可用内容 < 100 ms；慢区块不阻挡其他区块。
- 手机本地详情点击到可交互首屏 P95 < 300 ms，连续主线程工作尽量不超过 50 ms。
- 长录音首屏时间线 30–50 行，实际挂载行数接近可视区 + 预取，不一次创建全部 1,673 行。
- 常规列表刷新不执行递归文件扫描；播放进度更新不重建全文列表。
- 普通首屏响应尽量控制在 100–200 KB；证据及历史按需读取。

测试矩阵：冷启动、首次进入、30 秒后回到页面、连续切页、播放中滚动、同步中进入详情、人工标注后返回、离线查看；数据用当前规模及转写/审核增长后的规模。记录 p50/p95、SQL 数、响应字节、首帧/可交互时刻、长帧、内存与扫描次数。

正确性验证必须保留：人物记忆与互动数一致；媒体声音和过期/撤销标注的过滤一致；分页无漏句/重复句；全文搜索与全选覆盖全部数据；新版输入淘汰旧版结果；缓存不会复活已处理审核项；本地缓存离线可用。

## 7. 本轮判断边界

电脑人物慢查询已通过 SQL 计划、正式 HTTP 和隔离索引实验确认。手机全量布局、全量刷新、同步扫描和重复 JSON 解析由代码确认；各自占卡顿时间的比例需真机追踪。审核当前为空，本轮没有复现大量审核项下的长等待。应先修已证实的主要瓶颈，再用统一指标验证剩余页面，而不是直接对所有页面添加缓存或调整加载动画。
