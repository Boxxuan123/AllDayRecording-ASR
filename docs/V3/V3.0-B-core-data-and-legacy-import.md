# V3.0-B Core Data 与 Legacy Import 验收

> 状态：完成（2026-08-31）
> 前置阶段：[V3.0-A 基线与契约验收](V3.0-A-baseline-and-acceptance.md)
> 规格：[V3 重构规格](V3重构规格.md)
> 当前运行时修订（2026-09-02）：V3 现已默认启用，`migrate` 仍是根命令；
> B 阶段的 `legacy-import` 和 importer 已随 Legacy 运行时退役。本文件对默认关闭和
> 一次性 V2 导入的描述仅为历史实施记录。

## 1. 交付边界

V3.0-B 在 `allday_asr.v3` 下建立了独立 Core，不复用 V2 的巨型数据库类、页面服务
或模型实现：

- framework-free domain model、application use case、port 和显式 composition root；
- 独立 `core.sqlite3`、SQLite WAL、顺序 migration、外键和事务边界；
- Recording Catalog、Device、Processing Run、Artifact、Correction、Change Log、
  Audit、Idempotency、Tombstone 与 Legacy Import Run 仓储；
- SHA-256 内容寻址 Audio/Artifact Store、原子发布和稳定 media ID；
- query-only `LegacyV2Importer`，以 V2 数据库 SHA-256 作为默认 namespace；
- B 阶段曾提供 `migrate` 与一次性 `legacy-import` 管理入口；当前只保留 `migrate`。

B 阶段 V3 仍默认关闭；V3.0-G 后默认开启。当前版本显式设置
`ALLDAY_V3_ENABLED=0` 只会禁用 V3，不会启动 Legacy 运行时。composition root
的构造仍不创建目录或打开数据库，只有执行状态命令才会写入 V3 自有目录。

## 2. V3 自有数据布局

默认根目录为 `state/v3`，可通过 `ALLDAY_V3_STATE_DIR` 或 CLI `--state-dir`
覆盖：

```text
state/v3/
├── core.sqlite3
├── core.sqlite3-wal
├── core.sqlite3-shm
├── audio/<sha256-prefix>/<sha256>
└── artifacts/<sha256-prefix>/<sha256>
```

schema version 1 包含以下事实表：

| 范围 | 表 |
| --- | --- |
| Catalog | `recording_sessions`、`audio_assets`、`audio_replicas`、`capture_segments`、`session_manifests` |
| Processing | `processing_runs`、`artifacts`、`correction_operations` |
| Device/Sync 基础 | `devices`、`change_events`、`tombstones` |
| 可靠写入与审计 | `idempotency_records`、`audit_entries`、`legacy_import_runs` |
| Schema | `schema_migrations` |

原音内容、capture segment、artifact 和 correction operation 由数据库 trigger 保护，
不能原地更新或直接删除。可变资源使用正 revision；跨请求命令由 idempotency key
留痕，删除语义写入 tombstone，资源变化追加 change event。

## 3. Legacy V2 映射与保护

导入器使用 SQLite URI `mode=ro`、`PRAGMA query_only=ON` 和只读事务打开 V2，
不会在 V2 文件上建表、升级 schema 或写导入标记。

| V2 | V3 |
| --- | --- |
| `recording_sessions` | `RecordingSession` |
| `source_objects` | 以 SHA-256 去重的 `AudioAsset` |
| `source_instances` | 保留物理实例身份的 `AudioReplica` |
| `session_sources` | 保留顺序和时间范围的 `CaptureSegment` |
| `session_manifests` | 不可变 `SessionManifest` |
| `processing_runs`、`derived_artifacts` | `ProcessingRun` 与不可变 `Artifact` |
| 五类人工 identity/semantic 修正表 | `CorrectionOperation`，并保留原始表快照 |
| 其余已识别 V2 事实/评测表 | 内容寻址的不可变 JSON snapshot artifact |

稳定 V3 ID 由“V2 数据库指纹 namespace + 表 + V2 主键”派生；同一源库重复导入时，
session、asset、replica、segment、run、artifact 和 correction 均命中唯一键并计入
`existing`。每次执行仍生成独立 import batch 和审计记录。

报告的 `created`、`existing`、`issues` 和 `unmapped` 会显式区分新增、幂等跳过、
缺文件、摘要/大小不匹配、冲突路径、断裂引用、非法元数据和未知用户表。
`sqlite_*` 引擎元数据不会被误报为业务对象。

## 4. 验收证据

### 4.1 V3.0-B 专项

`python -m unittest` 对七个 V3 测试模块执行 28/28 通过，其中 B 新增 16 项：

| 规格验收项 | 自动化证据 |
| --- | --- |
| 空库可重复迁移；失败无半版本 | 重复初始化、WAL/外键检查和注入失败 migration 的 schema/version 回滚测试 |
| 同一 V2 库导入两次无重复 | 合成 schema-15 fixture 连续导入，核心事实表计数完全不变，第二次进入 `existing` |
| session 实例数、顺序、时长、SHA 一致 | 抽样 fixture session 的两段 source graph 逐字段 join 对比 |
| 缺文件、冲突路径、不可映射对象进入报告 | fixture 同时注入 missing path、同路径异 SHA、摘要不匹配和未知用户表 |
| V2 只读且摘要不变 | 导入前后对同一 V2 fixture 计算文件 SHA-256 并断言相等 |
| Core 测试不启动 UI/HTTP/模型 | AST 架构门禁禁止 domain/application/ports 导入 SQLite、HTTP、Vue/ArkUI 和模型库 |

此外对当前真实 V2 库只执行了 query-only schema 审计：schema 15、43 张用户表、
4 个 session、145 个 source instance、45 个 processing run。字段与导入器匹配，
已识别表均有直接映射或 snapshot 策略。此次阶段验收没有对真实音频和真实 V2
数据执行导入；真实数据双份备份、抽样核对和正式迁移仍属于 V3.0-G。

## 5. 显式操作入口

创建/升级一个隔离的 V3 Core：

```text
$env:ALLDAY_V3_ENABLED = "1"
allday-asr migrate --state-dir <v3-state-dir>
```

B 阶段曾在完成备份和人工确认后，通过一次性工具导入 V2 副本。该工具不属于当前
安装包；如需审计当时的迁移，应核对 release receipt、只读备份和 Git 历史，不要把
旧导入器接到当前 V3 state。

不要把 `--state-dir` 指向 V2 state 目录，不要在 V3.0-B 阶段对唯一一份真实库执行
导入。导入过程中发现的 quarantined session 必须先根据报告处理，不能静默提升为
`ready_for_processing`。

## 6. 阶段结论

V3.0-B 的 Core Data 与 Legacy Import 边界已经可独立测试和显式运行；V2 默认入口、
V2 数据库、Vue 页面、Watch/Phone 运行时和现有模型路径均未切换。下一阶段可以在此
Recording Catalog、Device 和 Change Log 基础上开始 V3.0-C 的可信设备接入与同步。
