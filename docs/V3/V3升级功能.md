可以，而且这个顺序已经很合理了：**先把现实对话还原准确，再建立可追溯的数据架构，然后先兑现“自动提醒”这一项高价值功能，最后逐步学习人物并形成长期记忆。**

不过有两处要稍微界定清楚：

1. **第一阶段就要做“说话人分离”和“我/非我识别”**，否则智能提醒难以判断是谁答应了什么。第四阶段做的不是基础分离，而是“未知人物跨录音聚类、用户命名、以后自动认人”。
2. **第二阶段的第三层先搭架构，不必把完整总结功能提前做完。** 先设计数据表、证据链、版本和重算机制；真正的每日总结与关系观察仍放在第六阶段。

整理后可以正式定成下面这六个阶段。

# V 3.1：建立可靠的统一对话时间线

> 开发状态（2026-08-31）：V3.1-A/B/C 工程实现完成。系统已经覆盖绝对时间、模型原始值/当前值、文本/说话人/本人身份联合校正、修订冲突、Desktop 精确原音回听、Phone 离线 outbox、`self/not_self/unknown` 三态身份门禁，以及跨切片边界漂移、CER、说话人连续性和重叠语音错位的内容哈希准入收据。真实本人正例和穷尽 alignment/speaker/overlap 真值仍不足，因此真实数据的两项自动门禁会明确拒绝；这属于待采集的验收证据，不是缺失的工程路径。

## 目标

把手表传来的录音可靠地还原成：

> 谁，在什么时间，说了什么。

这里的“谁”暂时只需要达到：

```text
self
speaker_01
speaker_02
unknown
```

不要求立刻知道 `speaker_01` 是张同学。

## 需要完成

```text
手表录音传输
→ 原始音频存储
→ VAD语音活动检测
→ 对话切片
→ ASR转写
→ 说话人分离
→ 我的声纹识别
→ 时间戳对齐
→ 统一utterance记录
```

统一记录类似：

```json
{
  "utterance_id": "u_1024",
  "audio_id": "audio_20260901_003",
  "absolute_start_time": "2026-09-01T10:23:15+08:00",
  "absolute_end_time": "2026-09-01T10:23:19+08:00",
  "speaker_track_id": "speaker_01",
  "person_id": "self",
  "speaker_confidence": 0.96,
  "text": "我下午把修改后的文档发给你",
  "asr_confidence": 0.91
}
```

## 完成标准

这一阶段结束时，应当满足：

* 每句话都有绝对时间；
* 每句话都有说话人轨道；
* 至少能比较可靠地区分“我”和“非我”；
* 每句话可以播放对应的原始音频；
* 用户可以修改转写和说话人；
* 原始识别结果与用户修正结果都能保留；
* 长录音切片后不会出现大面积文字与说话人错位。

这是整个项目最重要的地基。后面出现任何错误，都要能追溯回这里。

# V 3.2：建立三层数据架构

> 开发状态（2026-08-31）：工程实现完成。Contract `3.2.0`、Core schema `6`；证据跨度、事件操作历史/当前状态、记忆版本、生成 provenance、结构化 proposal 审批、递归失效与重算队列均已有 Core、Desktop API 和自动化测试。Phone projection 保持 `3`。本阶段不宣称生产 LLM 或自动总结已经接入，完整完成边界见 [V3.2 三层知识架构与可重算闭环](V3.2-three-layer-knowledge-architecture.md)。

## 目标

建立：

```text
第一层：证据层
第二层：事件层
第三层：记忆与解释层
```

这一阶段重点不是马上生成漂亮的总结，而是搭好一套以后不会失控的数据结构。

## 第一层：证据

包括：

* 原始音频；
* 音频片段；
* 转写；
* 时间戳；
* 说话人；
* 模型置信度；
* 用户修正记录。

## 第二层：事件

包括：

* 任务；
* 请求；
* 承诺；
* 约定；
* 决定；
* 修改；
* 取消；
* 人物事实；
* 重要经历。

需要同时保存：

```text
事件操作历史
+
事件当前状态
```

例如：

```text
创建：明天10点见面
修改：改到明天11点
取消：明天不见了
```

不能只留下最后的“已取消”。

## 第三层：记忆与解释

这一阶段先建立表和接口：

* 每日总结；
* 人物记忆；
* 人物事实；
* 关系观察；
* 互动统计；
* 模型推断；
* 生成版本。

暂时可以只放测试数据，不必在此阶段完整实现自动生成。

## 这一阶段必须做好三件事

### 1. 来源追溯

每个事件必须知道来自哪些话语：

```json
{
  "event_id": "evt_201",
  "evidence_utterance_ids": [
    "u_1024",
    "u_1025"
  ]
}
```

### 2. 版本记录

至少记录：

```text
使用的模型
提示词版本
提取程序版本
生成时间
输入数据范围
```

### 3. 失效和重算

例如用户把说话人从张同学改成王同学，系统应该能够：

```text
修改第一层身份
→ 找到受影响事件
→ 修正第二层人物关联
→ 让相关人物记忆和总结失效
→ 重新生成第三层
```

## 完成标准

* 三层数据可以分别查询；
* 第二、第三层都能追溯到上一层；
* 用户修正第一层后，能找出受影响的派生数据；
* 大模型只能提交结构化变更建议，不能直接随意改数据库；
* 同一批数据可以重新运行并生成新版本。

# V 3.3：智能提醒闭环

> 开发状态（2026-09-01）：工程实现完成。Contract `3.3.0`、Core schema `7`、Phone projection `4`；候选校验、确认门禁、去重与修订冲突、同事件更新/取消/完成、证据回听、Desktop 审核页、Codex 文本提取、Phone 投影和 HarmonyOS 系统定时提醒均已接通。Codex 使用专用空目录、只读沙箱和拒绝审批，候选默认进入审核；完整边界见 [V3.3 智能提醒闭环](V3.3-intelligent-reminder-loop.md)。

这是第一个真正面向用户的核心功能。

## 目标

识别对话中的：

```text
待办
请求
承诺
约定
提醒指令
修改
取消
```

并转换成真正可执行的提醒。

## 核心流程

```text
新对话进入
→ 检索相关上下文
→ 大模型输出候选事件
→ 程序校验
→ 去重与冲突处理
→ 自动创建或等待确认
→ 用户确认、修改、忽略
→ 反馈写回系统
```

## 第一版建议只支持六种操作

```text
CREATE_TASK
CREATE_APPOINTMENT
UPDATE_EVENT
CANCEL_EVENT
MARK_DONE
IGNORE
```

不要一开始支持几十种复杂事件类型。

## 提醒必须具备

* 标题；
* 行动主体；
* 相关人物；
* 时间；
* 地点；
* 置信度；
* 原话证据；
* 新建、修改或取消状态；
* 是否需要用户确认。

例如：

```json
{
  "operation": "CREATE_TASK",
  "title": "把修改后的文档发给张同学",
  "actor_person_id": "self",
  "related_person_ids": ["person_12"],
  "scheduled_time": "2026-09-01T16:00:00+08:00",
  "confidence": 0.91,
  "evidence_utterance_ids": ["u_1024"],
  "needs_confirmation": true
}
```

## 最重要的不是“能创建”，而是完整闭环

必须测试：

```text
“明天十点见”
→ 创建

“改成十一点”
→ 更新原事件，而不是新建

“明天不用去了”
→ 取消原事件

“刚才说错了，是周三”
→ 修正原事件

“我已经发了”
→ 标记完成
```

## 完成标准

用户能在一个候选提醒页面完成：

```text
确认
修改
忽略
播放原话
```

同时达到：

* 不重复创建同一件事；
* 可以正确修改旧提醒；
* 可以正确取消提醒；
* 可以区分“我答应别人”和“别人答应我”；
* 每个提醒都能播放证据；
* 错误提醒不会直接污染长期记忆。

完成前三阶段后，你实际上已经有一个独立可用的MVP了。

# V 3.4：增加未知说话人聚类和标注

这个阶段正式解决：

> `speaker_01` 到底是谁，以及今天的 `speaker_01` 和昨天的 `speaker_03` 是否是同一个人。

## 目标

建立开放集人物识别：

```text
已知是我
已知是张同学
可能是王同学
未知人物A
无法判断
```

“未知”必须始终是合法结果，不能强迫系统从已知联系人里随便选一个。

## 核心流程

```text
提取说话人embedding
→ 同一录音内聚类
→ 跨录音匹配
→ 形成未知人物簇
→ 用户听代表性片段
→ 用户标注人物
→ 建立或更新声纹档案
```

人物标注界面最好支持：

* 这是某个已有联系人；
* 创建新人物；
* 这几段不是同一个人；
* 合并两个未知人物；
* 拆分错误聚类；
* 忽略电视、广播和环境声音；
* 撤销之前的标注。

## 防止声纹库污染

只有下面两种数据可以进入稳定声纹库：

* 用户明确确认；
* 极高置信度且音频干净的识别结果。

普通自动识别结果不能无限自我学习，否则一次错误会逐渐把整个人物库带偏。

## 完成标准

* 同一个未知人物能够跨天聚合；
* 用户可以用少量代表性片段完成标注；
* 系统允许“无法识别”；
* 支持合并、拆分、纠错和撤销；
* 身份修正后，相关事件可以重新绑定；
* 每个人保存多个声纹原型，而不是只保存一个平均向量。

# V 3.5：建立跨天人物记忆

有了稳定的 `person_id` 后，才适合正式做人物记忆。

## 目标

回答：

```text
我和这个人最近发生过什么？
我答应过他什么？
他答应过我什么？
我们最近主要讨论什么？
还有什么没有完成？
```

## 每个人物可以建立这些数据

```text
基本身份
别名和称呼
关系标签
首次出现时间
最近出现时间
互动时间线
共同话题
我作出的承诺
对方作出的承诺
未完成事项
事实型记忆
近期状态
```

人物页可以先做成：

```text
张同学

最近互动：
- 今天讨论合同修改
- 昨天确认见面时间
- 上周讨论项目交付

我答应他的：
- 周三前发送修改稿

他答应我的：
- 明天带合同原件

近期话题：
- 合同
- 项目进度
- 见面安排
```

## 需要区分记忆类型

```text
稳定事实：
张同学是项目成员

偏好：
他通常不喜欢上午开会

短期状态：
他这周正在上海

计划：
明天上午见面

承诺：
他答应带合同

模型观察：
他最近似乎更关注交付进度
```

前五种也不应该一概永久有效，需要有：

```text
有效期
置信度
证据
是否由用户确认
```

## 完成标准

* 人物页面能展示跨天互动；
* 所有记忆可以跳回事件和原话；
* 支持添加、修改、撤销、过期；
* 同一句短期表达不会被错误升级成永久人物属性；
* 人物身份修正后，记忆可以迁移或重新计算；
* 承诺和未完成事项能与提醒系统关联。

# V 3.6：生成每日总结和关系观察

这是最终把系统从“数据记录器”变成“个人记忆助手”的阶段。

## 每日总结应该主要读取第二层

不要重新把全天原始转写全部交给模型，而是输入：

* 当天重要事件；
* 当天任务变化；
* 当天决定；
* 自己作出的承诺；
* 别人作出的承诺；
* 当天人物互动；
* 昨日遗留事项；
* 少量关键原话。

输出可以分成：

```text
今天发生了什么
今天做出的决定
新增待办
已完成事项
未解决问题
重要人物互动
值得记住的话
明天需要关注什么
```

## 关系观察应该读取更长时间窗口

例如过去7天、30天：

* 互动频率变化；
* 共同话题变化；
* 未完成承诺；
* 请求与回应情况；
* 合作事项进展；
* 明显分歧；
* 长时间未联系的重要人物。

但必须将结果分成两栏：

### 已验证事实

```text
过去7天与张同学交流4次。
存在两个尚未完成的协作事项。
你们主要讨论合同和交付时间。
```

### 模型观察

```text
你们最近的互动更加集中在项目交付上。
对方可能对时间安排较为关注。
```

模型观察需要显示：

* 证据；
* 时间范围；
* 置信度；
* 为什么得出这个判断；
* 用户可以纠正或删除。

## 完成标准

* 每日总结从事件层重新生成；
* 不使用“昨天总结续写今天总结”的方式；
* 客观统计由程序计算；
* 语言归纳由大模型生成；
* 事实与推断明确分开；
* 关系观察有时间窗口和证据；
* 用户修正底层数据后，相关总结可以重算。

# 最终阶段关系

你的六个阶段可以用这条主线来理解：

```text
第一阶段：听清楚
谁在什么时候说了什么

第二阶段：存明白
证据、事件和记忆如何组织

第三阶段：做事情
从对话变成提醒和待办

第四阶段：认出人
未知声音逐渐对应现实人物

第五阶段：记住人
把跨天经历、承诺和话题串起来

第六阶段：理解生活
形成每日总结与关系观察
```

还有一个很实用的边界：

```text
第一至第三阶段 = 可独立发布的提醒型MVP
第四至第五阶段 = 人物记忆系统
第六阶段 = 完整个人对话助手
```

所以这套安排可以直接定下来。唯一需要写进第一阶段任务里的，是：

> **第一阶段必须包含同一段对话内的说话人分离，以及“我/非我”判断；第四阶段才负责未知人物的跨天聚类、命名和自动识别。**

这样阶段之间不会出现依赖断层。
