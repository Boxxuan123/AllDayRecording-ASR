# V3.0-C Device Gateway 与 Phone 本地数据层验收

> 状态：工程实现完成，真机验收待执行（2026-08-31）
> 前置阶段：[V3.0-B Core Data 与 Legacy Import](V3.0-B-core-data-and-legacy-import.md)
> 规格：[V3 重构规格](V3重构规格.md)

## 1. 交付边界

V3.0-C 在既有 Passkey、HUKS、私有 CA、mDNS 和断点上传能力上增加受限的
Device API，并让 Phone 使用独立 RDB 保存移动投影和可靠同步状态：

- `/device/v3/status` 和 `/device/v3/sync` 只接受已登记设备的一次性 challenge 与
  HUKS 签名，不接受 bearer token 或 Passkey 回退；
- transfer trust adapter 将既有签名校验与 V3 scope、撤销、使用审计和稳定
  `receiver_id` 绑定起来；
- 已完成并验证摘要的 Phone 上传通过严格 manifest adapter 一次性进入 Recording
  Catalog，原音复制到 SHA-256 内容寻址仓库；
- `/device/v3/sync` 在一个 Core 事务中处理 outbox、操作幂等记录、增量 change log、
  cursor 与审计；
- Phone RDB 保存可重建投影、outbox、冲突、cursor、重试状态和本地音频关联；
- Phone 同步响应在单个 RDB 事务内按 receipt、change、cursor 的顺序应用，cursor
  最后提交；中途异常会回滚整个响应。

本阶段没有开放 Desktop 管理 API、Lab API、绝对文件路径访问或任意资源查询。
V3 Device API 与桌面管理面继续保持不同的接口与授权边界。

## 2. 信任与接口边界

Device 请求沿用同一个信任根：首次扫码由 Passkey 授权并登记 HUKS 公钥，随后由
设备密钥签署规范化的 method、path、query、body digest 和一次性 challenge。
challenge 只能使用一次，请求路径和内容变化会使签名失效。

默认 Phone scope 为：

| Scope | 能力 |
| --- | --- |
| `device.status` | 读取 Device V3 contract/projection 状态 |
| `audio.upload` | 使用受限的断点音频上传路径 |
| `data.sync.read` | 拉取允许进入 Phone 投影的 change event |
| `data.sync.write` | 提交 Phone outbox 操作 |

设备撤销后，新的 challenge、上传和同步都会被拒绝。每次授权使用和拒绝结果都写入
V3 审计。发现仍只使用 mDNS 中的稳定 `receiver_id`；TLS 继续校验首次配对导入的
私有 CA，不因 IP 或 Wi-Fi 变化降级为不受信连接。

Device V3 错误统一返回 `code`、`message`、`details` 和 `request_id`。未注册的路径
保持 404，不能借 Device 身份进入桌面管理和实验接口。

## 3. Core schema 与同步语义

Core schema version 2 在 V3.0-B 的事实表之外增加：

| 表 | 用途 |
| --- | --- |
| `device_credentials` | 设备公钥映射、scope、撤销和最近使用时间 |
| `pairing_records` | `device_id` 与稳定 `receiver_id` 的配对事实 |
| `sync_cursors` | 每设备、每 projection version 的已确认位置 |
| `client_operations` | `operation_id`、内容摘要、终态 receipt 和幂等重放 |

同步 contract version 沿用 V3 contract，Phone projection version 为 1。cursor 使用
单调 change sequence 编码。服务端先按 canonical JSON 计算 operation 摘要：完全相同
的 `operation_id` 重放返回已保存 receipt，不再次执行；相同 ID 携带不同内容返回
冲突。当前 V3.0-C 只交付同步基础设施，尚未由后续领域用例注册的 Phone 写操作会
得到持久的 `rejected` receipt，而不会被静默丢弃。

完整 change log 会保留足够的 projection payload。schema 2 migration 会为 V3.0-B
已有的 recording session、audio asset 和 processing run change event 回填 payload，
因此从 `cursor-0` 可以重建 Phone 投影。

Phone 上传 adapter 只接受完成态上传和固定 manifest v1 字段，校验 WAV 大小、分块、
摘要和引用关系，不接受调用方指定任意目标路径。相同 manifest 幂等重放不会重复创建
session、asset、replica、segment 或 change event；同一 session key 配不同 manifest
会被拒绝为冲突。

## 4. Phone RDB 与恢复策略

Phone 使用 `phone_v3_projection.db`（RDB SecurityLevel S2），数据库 schema version 2，
业务 projection version 1。schema upgrade 在事务中执行；version 2 为旧库的
`sync_state` 增加持久 `retry_count`。

| 数据类别 | 表/状态 | 重建时处理 |
| --- | --- | --- |
| Computer 副本 | recordings、audio assets、processing runs、utterances、review items、tombstones | 清空并从 `cursor-0` 拉取 |
| 待同步写入 | `outbox` | 保留 |
| 冲突证据 | `conflicts` | 保留 |
| Phone 原音事实 | `local_audio_links` | 保留 |
| 同步状态 | `sync_state` | cursor 复位，错误与重试状态由后续同步更新 |

每个响应在同一事务中先处理 terminal receipt，再应用有序 change，最后更新 cursor。
任何一步失败都 rollback，因此重启后会从旧 cursor 重放。upsert、tombstone 和服务端
operation receipt 都是幂等的，重放不会产生重复行。

网络失败会保留 outbox，并持久增加操作尝试次数和同步 `retry_count`。Phone 使用指数
退避重试，最长五分钟；应用重启后会根据 RDB 中的失败状态恢复重试。上传成功与状态
同步分离：后续同步失败不会把已经安全上传的本地音频标成失败或删除。

## 5. 启用方式

V3 listener 仍默认关闭。使用隔离的 V3 state 目录显式启动：

```text
$env:ALLDAY_V3_ENABLED = "1"
allday-asr transfer receive --enable-v3 --v3-state-dir <v3-state-dir>
```

仍应沿用现有 transfer TLS、receiver identity 和配对配置。不要把
`--v3-state-dir` 指向 V2 state 目录，也不要为了调试关闭证书校验或改用 bearer token。

## 7. 阶段结论

V3.0-C 的 Device Gateway、信任 scope、Catalog ingest、批量同步、Phone RDB、原子
cursor、全量重建和离线重试已完成工程实现，并通过可在当前环境执行的自动化门禁。
阶段尚未宣告产品验收完成：真实 Phone 的一次授权/静默认证、Wi-Fi/CA 切换和飞行模式
冷启动仍是明确的外部验收项。后续 V3.0-D 可以基于已稳定的 change log 和 Phone
projection contract 开始持久处理编排，不应绕过本阶段的 Device API 权限边界。
