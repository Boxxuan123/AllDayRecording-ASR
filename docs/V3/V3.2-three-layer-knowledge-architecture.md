# V3.2：三层知识架构与可重算闭环

## 当前结论

- 状态：V3.2 工程实现完成。
- 日期：2026-08-31。
- Contract `3.2.0`，Device projection `3`，Core schema `6`，Phone projection schema `6`。
- V3.2 建立数据结构、命令边界和测试闭环，不宣称已经接入生产 LLM，也不提前实现 V3.3 的自动提醒策略。

## 三层边界

第一层是不可替代的证据：原始 `AudioAsset`、真实 `CaptureSegment`、统一
`Utterance`、原始/当前文本与说话人、身份决策、`CorrectionOperation`，以及新建的
`EvidenceSpan`。`EvidenceSpan` 同时保存 session 坐标和原始 asset 坐标；一条话语跨越
采集分片时会产生多条 span，不制造整段伪音频，也不丢失对应 artifact 和 media。

第二层由两个对象组成：

- `EventOperation` 是不可变操作账本，按事件 revision 保存 create、update、cancel、
  complete 和 reopen；
- `EventCurrentState` 是可重建的当前投影，保存业务状态和合并后的结构化 payload。

修改或取消不会覆盖旧操作。事件类型只允许 task、request、commitment、appointment、
decision、person_fact 和 important_experience；V3.3 可以在这些稳定对象上实现提醒策略，
而不需要再定义一套页面专用事件 JSON。

第三层使用版本化 `MemoryRecord`，覆盖 daily_summary、person_memory、person_fact、
relationship_observation、interaction_statistic 和 model_inference。V3.2 只建立表、接口、
测试数据通路和版本规则，不把 fixture 内容冒充真实总结。

## 模型写入边界

模型或提取器不能直接写事件当前表和记忆表。唯一入口是
`POST /api/v3/knowledge-generations`：

1. 提交 producer、producer version、model、prompt version、extractor version 和输入范围；
2. Core 解析并冻结实际 utterance/event revision，计算 canonical input SHA-256；
3. Core 严格验证结构化 proposal 和证据所属 session；
4. proposal 进入 pending 队列，但不改变事件或记忆；
5. 独立 accept 命令才在同一事务中写操作账本、当前投影、证据链接和依赖边；reject 只留审计收据。

同一 producer 配置和同一输入摘要可以重复提交，每次分配递增 generation number；生成记录
和 proposal 都保留，因此结果可复现、可比较，不靠覆盖旧 JSON 表示“重跑”。

## 来源追溯与失效传播

`EvidenceLink` 保存事件到 utterance、记忆到 event（以及可选的直接 utterance）的版本化
来源。事件当前查询会累计返回所有历史 revision 的证据，事件操作历史仍显示各次操作自己的
直接证据。

`DerivationDependency` 是跨层通用依赖边。用户修订 utterance 时，Core 在原有 Artifact
失效逻辑之外执行递归闭包：

```text
utterance revision changed
→ affected event revisions stale
→ affected memory revisions stale
→ append immutable InvalidationEvent
→ enqueue durable RecomputeRequest
```

新的事件 revision 被接受后，对应 event 重算请求标为 succeeded；使用新事件 revision 生成
同一 memory ID 的新版本后，对应 memory 重算请求也标为 succeeded，旧 memory 版本保留并
标记 stale/superseded。失败不会删除证据、操作历史或旧生成结果。

## Desktop API

- `GET /api/v3/evidence-spans?session_id=...`
- `GET /api/v3/events?session_id=...`
- `GET /api/v3/events/{event_id}/operations`
- `GET /api/v3/memories?session_id=...`，或使用 subject type/id 查询
- `POST /api/v3/knowledge-generations`
- `GET /api/v3/knowledge-proposals`
- `POST /api/v3/knowledge-proposals/{proposal_id}/accept|reject`
- `GET /api/v3/derivations/affected`
- `GET /api/v3/invalidations`
- `GET /api/v3/recompute-requests`

这些端点只存在于 loopback Desktop API。V3.2 没有把三层知识资源推入 Phone change log，
所以 Device projection 保持 `3`，手机不会意外收到未声明的 resource type。

## 数据保护与恢复

- EvidenceSpan、EventOperation、MemoryRecord、EvidenceLink、DerivationDependency 和
  InvalidationEvent 均有数据库触发器禁止更新或直接删除；
- EventCurrentState 是操作账本的受控投影，写入使用 expected revision 防并发覆盖；
- proposal 的接受、投影更新、来源链接、依赖边和审计写入位于同一 SQLite 事务；
- 失效只追加状态事件与重算请求，不回退已经验证的原音、备份或 processing run；
- schema v6 迁移保持连续、可重复执行，并继续通过 foreign key check 和 WAL 门禁。

## 自动化验收

V3.2 专项测试覆盖：

- 三层表、索引、外键和不可变触发器；
- 跨 capture segment 的 EvidenceSpan 物化；
- proposal 提交不产生业务写入，接受后才创建事件/记忆；
- create/update 操作历史与当前状态同时正确；
- 同输入重复生成分配新 generation number；
- utterance 修订递归失效 event 和 memory，并创建重算请求；
- 接受新 event/memory revision 后重算请求闭环为 succeeded；
- Desktop 查询/命令路由、错误边界和 OpenAPI/JSON Schema；
- Harmony 消费收据继续固定 projection `3`，并校验新的 canonical manifest/fixture digest。

本次验收中，Core 全量测试、Python lint、Desktop 前端单测/生产构建、Harmony host 单测与
Code Linter 均通过。Harmony clean debug 构建完成 ArkTS 编译和 unsigned HAP 打包，但当前
DevEco 签名工具读取 watch HAP 时以 `Invalid CEN header (invalid zip64 extra data field size)`
失败；串行、非增量重试结果一致，因此该环境的签名产物不计为通过，也不把它归因于 V3.2
源码或契约编译。

真实 LLM 自动提取准确率、自动接受策略、提醒触发、跨天人物实体和总结质量不属于 V3.2
完成声明；它们分别留给 V3.3–V3.6，并必须继续使用本阶段的 proposal、provenance、
dependency 和 invalidation 接口。
