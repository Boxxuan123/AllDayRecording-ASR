> 本文记录修复前的诊断快照。后续恢复结果见 [2026-09-27 录音恢复记录](session-recovery-20260927.md)。

## 结论

2026-09-27 对手机接收索引、手机投影数据库的只读副本、电脑接收目录和 Core 数据库进行了核对。最新录音的完整音频已经到达电脑，但过早提交的一分钟会话清单冻结了入库范围。后续清单被拒绝，导致重复校验和转写范围停留在第一分钟。

本轮完成诊断和隔离复现；未修改业务代码、正式数据库、设备数据或原始录音，未重启服务或重新转写。

这里同时存在两类问题：上传与入库流程没有正确判定整场录音完成，进度界面也没有正确表达和清理任务状态。只修改进度条显示条件，无法恢复后面的转写。

### 1.1 为什么之前不显示，新传入录音后才显示

这与“没有待备份任务”和“产生了一条无法完成的待备份任务”有关，同时受到进度清理缺陷影响。

| 场景 | 后台行为 | 当前界面表现 |
| --- | --- | --- |
| 页面刚初始化，只有已完成备份的旧录音 | 文件回执齐全，备份函数直接返回，没有上传进度回调 | `totalFiles` 初始为 0，不显示录音上传进度 |
| 新录音的第一片到达 | 本地变化触发自动备份，进度回调设置当前录音及文件总数 | `totalFiles > 0`，开始显示新录音进度 |
| 同一录音后续分片到达 | 分片上传后尝试提交更长的清单，但旧清单占用同一路径 | 文件虽然到达电脑，整场备份仍失败；进度可能接近完成 |
| 再点击同步 | 缺少完整回执的最新录音再次被选中，已有文件逐个校验和跳过 | 又看到这条录音的进度；不代表所有音频字节再次传输 |
| 没有实际传输，但保留了上轮进度 | 新调度路径未清空旧进度，页面只判断历史文件计数 | 旧进度条仍可能留在页面上 |

因此，“新录音传入后第一次出现进度”本身合理；“反复处理同一条、不能完成、结束后仍留着旧进度”需要修复。

用户已确认只看到最新录音的位置是同步进度区域。该区域表达当前任务，并非录音历史列表。历史录音的回执齐全，只有最新这条不完整，所以反复显示它。上传队列实际上按会话时间从早到晚取待备份项，不是只支持最新录音。

### 1.2 为什么旧版本或此前操作没有暴露问题

代码历史可以确认两处变化：

1. `8badf92` 之前，本地录音发生变化只触发列表刷新；该提交之后还会自动触发电脑备份。这个变化允许手机在手表仍向手机传输后续分片时，立即把已收到的第一片提交给电脑。
2. 旧的手动同步入口会先把 `computerProgress` 和 `completedSessionKeys` 清空；当前启用调度器时，入口直接 `trigger(true, true)` 并返回，绕过了这段初始化逻辑。

如果此前通常在手机收齐整条录音之后才点击同步，第一次生成的就是完整清单，路径冲突也就不容易出现。自动备份增加后，这个原先缺少完整性约束的流程更容易在正常接收过程中触发。

以上是代码变化和此次数据时间线支持的解释；没有此前每次点击的运行日志，不能把过去所有“未显示”的情况归为同一个原因。

## 2. 根因和代码位置

以下手机路径相对 `AllDayRecording` 工程，电脑路径相对 `AllDayRecording-ASR` 工程。

### 2.1 接收一片就启动备份，却把当前文件集合当成最终清单

- `phone/src/main/ets/v3/presentation/PhoneV3ViewModel.ets`：`onLocalAudioChanged()` 直接调用 `coordinator.trigger(true)`。该自动备份触发点由 9 月 26 日提交 `8badf92` 引入。
- `phone/src/main/ets/v3/data/PhoneV3ComputerBackup.ets`：读取当时本地文件快照并开始备份，没有等待整场录音的结束证据。
- `phone/src/main/ets/computer/ComputerSessionManifest.ets`：根据当时可见 WAV 重建清单；当前分片从零开始且连续，就会给出 `continuityValid=true`。连续并不能证明录音已经收齐。
- `phone/src/main/ets/computer/ComputerRecordingUploadService.ets`：每次上传快照内的 WAV 后提交同一路径 `session_summary.json`。

因此，手表向手机传输完整录音的过程中，手机收到第一分钟后便可能提交单片清单。

### 2.2 清单不可变，后续分片无法加入同一已入库会话

- `src/allday_asr/v3/interfaces/transfer/store.py`：同一路径的新内容会触发 `UploadConflictError`，错误为“接收路径已有不同内容，服务不会覆盖”。
- `src/allday_asr/v3/adapters/transfer/ingest.py`：即使绕过文件路径冲突，同一会话的不同清单哈希仍会触发“同一 Phone 会话已提交不同的清单内容”。

在 `outputs/sync-diagnosis-20260927/` 内用独立 UploadStore 复现：先完成 1 片清单，再提交 71 片清单，稳定出现路径冲突。正式接收目录未被修改。

### 2.3 手动同步反复校验最新录音，界面还混用了两类状态

- `ComputerRecordingBackupService.ets` 只有在清单成功提交后才保存该轮分片回执。后续清单失败，因此这条录音仍被 `recordingsNeedingComputerBackup()` 选中。
- `ComputerRecordingUploadService.ets` 对电脑已有的文件会校验并跳过；进度增加不等于音频字节再次完整上传。
- `PhoneSyncCoordinator.ets` 会阻止冲突自动无限重试，但手动同步会解除阻止，再次尝试同一清单。
- `PhoneV3RecordingListPage.ets` 仅按 `computerProgress.totalFiles > 0` 显示进度，并使用 `computerSyncError/computerSyncMessage`；备份实际错误存放于 `backupError`。
- 当前调度器路径会在 `synchronize()` 提前返回，绕过旧路径中的进度清空；备份结束也缺少统一清理。
- `PhoneV3UseCases.ets` 的 `uploadStatus()` 会从已有链接取一个状态，不能证明全部本地分片已备份；`PhoneV3RecordingListPage.ets` 还可能因已有 sessionId 或旧 completedSessionKeys 提示已完成。

用户已确认“只显示最近录音”指同步进度区域。原因是历史录音已具备回执，只有最新这条持续处于待备份状态；此次不属于历史录音列表丢失问题。

## 3. 推荐修复顺序

### P0：补齐当前录音，恢复完整转写

1. 根据已校验的 71 个分片生成完整清单，保留原单片清单及处理记录。
2. 增加受控的会话补全入口：要求设备和会话身份一致、旧分片逐项哈希及时间位置不变、新分片只追加、全长连续。通过事务追加缺失的 70 个 capture segments，增加输入版本，并记录清单版本与审计事件。
3. 对完整输入重新验证备份覆盖范围，创建新的处理运行；已完成的一分钟运行不能被自动流程当成完整结果复用。
4. 新结果验证成功后切换当前结果；旧结果保留可追溯，对已存在的人工校正明确处理映射或冲突。
5. 电脑确认完整清单与版本后，手机补齐逐文件回执并刷新会话状态。

不要只覆盖接收目录的 JSON：Core 中的分片、备份证据和处理输入版本也必须一起更新。只重跑当前 ASR 仍会处理那一个已入库分片。

#### 恢复入口的具体要求

- **预检**：目标必须是同一会话；已有第一片的文件哈希、样本位置、格式保持一致；追加的 70 片连续，总样本数为 67,641,280。执行前再核对这些条件，避免依赖本次检查后可能变化的状态。
- **保存修复依据**：保留旧清单，新增完整清单版本，记录旧、新摘要和补全原因。修复工具先提供预览，列出将新增的分片、旧结果和受影响的派生数据。
- **原子入库**：在同一事务中更新分片映射、会话结束时间和输入版本。若同时到达重复补全请求，只允许一个成功，其余按相同摘要返回同一结果。
- **重建处理条件**：原 60 秒备份证据不能代表 70 分钟全部音频；完整备份复核通过后，将新输入版本送入处理队列。自动流程必须检查输入版本，不能只看到旧任务 succeeded 就返回完成。
- **发布完整结果**：新运行成功后切换当前转写和相关派生状态。旧七条转写、人工修改、说话人标注及其依据保留；可确认对应的修改迁移，不确定的映射进入待核对状态。失败时保留旧结果并标明仅覆盖第一分钟。
- **手机收尾**：同步完整清单确认和逐文件回执；71 个分片全部对应后，移除待备份状态、旧错误和旧进度。重新点击同步应没有新上传音频字节。

接收目录里已经有 71 个音频文件，恢复工作可以复用经过复核的现有文件，不需要要求用户重新从手表发送整段录音。

### P0：明确“文件已传完”和“整场录音已结束”

1. 手表传递可信的会话结束记录：会话 ID、是否已结束、最终片数、总样本数和清单摘要。恢复录音也要有显式结束状态。
2. 手机可随到随传 WAV，逐文件保存电脑确认；只有最终清单列出的分片全部接收并验证后，才提交会话完成请求。
3. 电脑接收未完成的分片时保持 receiving 状态；确认最终清单后才触发完整转写。文件按哈希保持不可变，清单通过版本管理保存。
4. 没有结束证据的旧协议录音显示“完整性待确认”，提供显式确认/兼容流程。短暂停顿和单次传输批次结束都不能独立证明整场录音已经结束。
5. 若产品后续需要边录边转写，另行支持带输入版本的部分结果，并明确显示已处理时长；不能继续复用完整会话的完成状态。

#### 建议的完成记录与确认流程

以下为设计建议，尚未实现：

| 数据 | 用途 |
| --- | --- |
| `sessionKey`、来源设备身份 | 确认这些分片属于同一场录音 |
| `closed`、`manifestRevision` | 确认录音已经结束，并识别当前清单版本 |
| `expectedSegments`、`totalSamples` | 明确最终应该收到多少片、多少音频样本 |
| 每片序号、样本起点、样本数、大小及 SHA-256 | 检查缺片、重叠、替换和损坏 |
| 最终清单摘要 | 让手机与电脑确认的是同一个完整输入 |

如果手表现有最终汇总能提供部分字段，可以复用；需要补齐“来源已结束”和最终文件集合的可验证语义，而不是由手机把当前目录中的文件推定为最终集合。

完整流程：

1. 手表产生并封口 WAV 分片；手机接收验证后可立即向电脑上传。
2. 电脑逐文件确认哈希和大小，手机保存对应回执。清单提交失败时，已成功的文件回执仍然保留。
3. 手表停止录音后提供最终完成记录；手机检查列出的所有分片均已收到。
4. 手机发送带版本的最终清单；电脑核对文件、连续性、最终总样本数及来源身份。
5. 电脑返回会话级确认：会话 ID、已确认的清单版本与摘要、片数、总样本数。
6. 只有收到匹配的会话级确认，手机才能显示“整条录音已备份”；只有当前输入具备完整备份证据，电脑才能启动完整处理。

单片传输完成、Wi-Fi 一次传输批次结束、几秒没有新文件，以及 `continuityValid=true` 都不足以替代最终完成记录。例如，第一分钟也完全连续，但并不代表录音到此结束。

#### 幂等、并发及兼容规则

- 同一最终清单重复提交，返回之前的确认结果，不重复入库或转写。
- 同一会话不同内容的清单不能简单覆盖。正常接收阶段允许累计分片；已确认的最终清单发生变更时，进入显式补全/修订流程。
- 补全时只接受旧分片原样保留、追加分片合法的情形；旧音频被替换应返回明确冲突。
- 清单和分片回执持久化，应用重启后根据电脑确认状态恢复，不能只依赖内存中的完成集合。
- 上传文件回执与会话完成回执分开保存，并绑定接收端身份和清单版本。任何一个文件 uploaded 都不代表整个会话 completed。
- 旧手机向新电脑提交缺少结束证据的清单时，应进入待确认状态；新手机连接旧电脑时，需要能力检查，避免继续提交可能增长的最终清单。
- 服务端、手机和手表按兼容能力分阶段更新；没有可靠完成证据时先保存分片，完整会话的提交等待明确确认。

### P1：修复进度、错误和录音状态

1. 进度绑定 `backupActive` 及本轮任务 ID；开始、完成、失败和无新文件时统一收尾，清理旧活动文件和完成集合。
2. 录音备份显示 `backupMessage/backupError`；标注与状态同步使用自身提示。清单冲突应明确显示“音频已到电脑，录音清单待补全”。
3. 分开统计“新上传字节”“已存在文件”“待确认清单”，无新增音频时避免显示成整段重新上传。
4. 录音级“已备份”要求当前清单版本确认且所有分片都有有效回执；不能因首片 uploaded 或 sessionId 非空就判定整场完成。
5. 保留全部历史录音，单独显示当前任务及待备份数量。一个会话冲突应保留失败状态并允许其他独立会话继续处理。

#### 推荐的用户可见状态

| 实际状态 | 推荐提示 | 进度行为 |
| --- | --- | --- |
| 没有新文件或待确认任务 | 已同步，没有新录音 | 不显示上传进度 |
| 手表仍在录音或手机仍在接收 | 正在接收录音，已收到 N 片 | 显示接收情况，不宣告整条完成 |
| 有音频字节上传 | 正在备份：新增 N 片，已传 X / Y | 显示本次实际上传进度 |
| 仅核对已有文件 | 正在核对电脑已有文件 | 简短校验提示，避免显示为重新上传全部录音 |
| 音频已到电脑，清单尚未确认 | 音频已传完，正在确认完整录音 | 保持“确认中”，不能显示整场成功 |
| 清单冲突 | 音频已保存，录音完整性确认失败 | 停止活动进度，保留具体错误和处理入口 |
| 完整清单已确认 | 已备份 70 分 27 秒，等待转写 | 收起活动进度，显示会话状态 |
| 转写进行中 | 正在转写，已处理 X / Y 分钟 | 使用处理任务的进度，不复用上传进度 |

进度的生命周期由任务状态驱动：每轮创建任务 ID；旧任务回调不得覆盖新任务；任务结束、失败或取消时清空活动文件。成功可短暂提示后收起，失败保留文字和重试入口。仅检查 `totalFiles > 0` 不能表达这些状态。

对于同一清单冲突，普通“同步”不应每次重新扫描整段录音。应保存冲突及对应版本；输入有变化、完成补全或用户明确选择重试时再尝试。网络超时与数据冲突分别处理；其他录音继续进入队列。

### 3.1 实施顺序与交付边界

1. **先补防线和回归用例**：服务端区分接收中与最终确认；客户端阻止接收未完成时提交最终清单，同时修正错误显示。单纯延迟几秒不能作为完成判定。
2. **实现可靠收尾和补全能力**：加入完成记录、版本化清单、逐文件/整会话两级确认，并保证重启和重试可恢复。
3. **执行当前录音的受控修复**：复核现有 71 片、补全输入、验证全量备份并重新转写。新处理失败时保留旧结果和修复记录。
4. **完善进度和队列**：按任务生命周期收尾、区分校验与上传、隔离单条录音的冲突。
5. **真机验收后发布**：覆盖手表到手机接收尚未结束、手机到电脑同时备份的真实并发场景。

## 4. 验收条件

- 先收到第 1 片，延迟收到第 2～71 片：最终输入必须覆盖 71 片、4,227,580 ms；首片到达不能提前宣告整场完成。
- 在第 1 片、第 35 片、最终清单确认前分别重启/断网：恢复后不遗漏、不重复建会话，不把部分回执显示成完整备份。
- 同一最终清单重复提交幂等成功；只追加的合法补全可审计；修改旧分片的清单被拒绝。
- 无新录音时重复点击同步：新上传音频字节为 0；进度正常收尾；错误能够在录音页看到。
- 一个会话失败不阻塞其他会话；手机和电脑的历史列表完整保留。
- 用一分钟前后均有语音的受控样例验证跨分钟转写。真实录音验收以输入覆盖和处理窗口完整为准，不能要求静音尾部也产生文字。
- 在没有新录音的情况下进行标注或状态同步，不出现旧录音的上传进度；完成新录音后再次同步，也不残留上轮进度。
- 同步状态成功而录音备份失败时，录音页和同步中心均准确显示备份错误，不能被其他同步成功提示覆盖。
- 手机与电脑同时断线恢复、重复完成请求并发到达时，会话数不增加、输入版本不重复升级、处理任务不重复创建。
- 修复现有会话后，Core 分片数为 71、输入覆盖 4,227,580 ms，手机回执完整，最新转写绑定新输入版本；旧的一分钟结果仍可追溯。
