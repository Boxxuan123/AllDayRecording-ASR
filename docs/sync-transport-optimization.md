# 同步传输与首次快照优化（2026-09-27）

## 实现

- 连接验证状态携带 V3 协议与能力信息，手机同一连接会话复用验证结果，省去重复 V3 状态及其认证挑战请求。旧服务缺少该字段时回退原流程；配置变化检查保留。
- 接收器使用 HTTP/1.1、Content-Length 和 TCP_NODELAY。未消费请求体的错误响应关闭连接，防止残留数据影响下一请求。响应附带连接 ID；手机日志记录原生连接复用标志及 DNS/TCP/TLS 耗时，旧系统不支持的指标显示 unknown。
- 协商 adaptive-batch-v1：上行起始 32 条，在 4–128 条内按服务器写事务耗时调整，仍受完整 UTF-8 请求 64 KiB 硬上限约束。下行起始 256 KiB/500 条，按手机落库耗时调整至 16 KiB–1 MiB、16–500 条。服务器事务计时从获得写事务后到提交完成，排除网络与读投影时间。
- 下行字节预算按未压缩 JSON 估算，包含回执开销。至少发送一个资源以推进游标，因此单个大资源或回执较多时可超过目标预算；不是新的硬性响应限制。
- 客户端声明 gzip 时，超过 4 KiB 的 JSON 使用 gzip level 1，只有变小才发送压缩数据。手机接收二进制并兼容平台已解压的响应；校验 gzip、CRC 和解压大小（32 MiB 上限）。
- 协商 snapshot-v1：初次同步固定变更序号 H，每个资源只发送 H 之前最后一个事件（包含删除）。分页游标保存 H 和当前位置，支持重启续传；结束切回 cursor-H，继续接收 H 之后的增量。分页查询使用只读事务，写事务只处理操作、回执与设备确认。手机继续原有回执、投影、游标原子提交。
- 兼容旧协议：未声明能力的客户端保留历史增量模式。新增字段均为可选，本轮不增加数据库迁移。前一轮已存在的电脑 schema 17、手机 schema 12 源码迁移保持原样。

## 验证与边界

- 真实本地 TLS 接收器：gzip、identity、gzip;q=0 连续请求复用同一 socket 和连接 ID；合成大 JSON 压缩后不足原大小的 10%。这不是实际用户数据压缩率。
- 1,200 条历史事件、60 个资源：首次快照只发送 60 条最新记录，分页中并发更新、删除、新增三个事件均通过后续增量收到；重建服务后继续游标，最终状态与完整历史重放一致。
- 快照读取期间另一个写事务可成功提交；验证字节分页、单资源超预算仍前进、非法未来游标拒绝。
- 电脑相关回归 182 项通过，上传回归 13 项通过。手机 12 组主机专项脚本通过，包括新增 check-sync-transport.cjs；gzip 测试使用 Node zlib 适配原生接口，不等同于真机解压验证。
- 手机正式签名包构建通过，手机和手表 Hypium 142/142 通过，DevEco Code Linter 0 缺陷，Ruff 与两端协议一致性检查通过。手机连接复用诊断已加入，但本轮尚未部署并采集真机日志，因此未宣称 Harmony 原生网络栈端到端复用已实测。
