# Agentic RAG 0.8.9：后续追踪、协议修复与新真实模型验证

本轮仅修复跨会话后续追踪、工具参数和事件时间协议，并补充超时分层证据。没有扩展人物规则或搜索架构，没有放宽预算，没有部署。

## 失败定位与修复

1. **跨群追踪有实际实现缺口。** `InvestigationTools.related()` 将起始群的动态 `source_contacts` 带入关系扫描的 SQL，导致只能看到原群的同账号发言。旧正例通过原生私聊目录的同账号匹配偶然取得后续，未覆盖“第二个群再遇到另一参与者”。修复只清除自动识别起始群造成的动态限制，随后仍与不可变 `root_scope` 取交集；用户显式指定的会话、账号、人物、来源、日期不被扩大。新增离线回归确实走起始群 → 协作群 A/B → 次日私聊 B。
2. **上下文工具参数不一致。** 旧真实输出把源证据 ID 放在 `evidence_ids`，而执行器只处理 `targets`，形成空操作。schema 明确二者含义，提示给出通用关联追踪参数；对上下文/原文工具中 `targets` 为空、支持证据为 1–4 条的旧输出做无歧义规范化。未知 ID 和授权校验不变；缺少必要参数或目标类型错误时明确拒绝。依赖动作无命中仍可正常返回空结果。
3. **unknown 事件时间定义不一致。** 旧提示只说日期留空，校验却要求日期、证据 ID、引文全部留空。schema 现在用两个 `anyOf` 分支表达未知/有依据时间；未知四字段只能为 `""`，原文引用保留在 claim 的 citations。明确时间仍验证完整日期引文，相对时间仍锚定消息的本地日期，不以查询日期代替。
4. **超时证据不足。** 旧回执只能定位到父执行器的 25 秒截止，不能倒推 SDK 内部具体阶段。现在记录 worker 启动、SDK 导入/初始化、thread_start、turn_submit、turn_wait、结果校验、SDK 关闭和写回的单调时钟事件。SDK 的公开 `thread.turn(...).run()` 与原 `thread.run(...)` 调用链等价，提交响应返回后才标记 turn_wait。计时仅保存阶段名称和耗时，不保存思维链或流式内容；超时错误指明最后阶段，仍只终止独占 Windows Job。
5. **验证时钟污染。** 旧夹具改写共享 `time.time`，虚构日期也会影响执行器持久化截止时间。验证入口在建夹具后恢复真实墙钟，仅给 HistoryRecall 注入虚构查询时钟；模型预算仍使用真实单调时钟/墙钟。另修正执行器对 SDK `usage.total.totalTokens` 嵌套用量的读取，使已有 token 上限正确计数。

## 固定预算与边界

每题最多两次模型调用，每次最多 25 秒；单题总期限 60 秒。每轮最多四个动作、单题八个工具、最多四个目标分支；远端 12 次来源请求、6 次检索请求、100 条记录上限未改变。最多三个新虚构案例、总计不超过 6 次调用和 180 秒；无自动重试，不以放宽超时解决失败。

沿用已有 SQLite 缓存、原生会话目录和人工确认的人物链接。成员、角色和同名账号规则未新增。关联会话只证明稳定账号的发言关系，不证明同名事件相同；事件锚点、原文、后续更正与来源限定仍需分别核对。缓存不足或证据截断保持 partial；本轮不验证私人历史覆盖率。

## 真实模型结果：检索链 3/3，端到端答案 0/3

实际发起 6 次，完整套件耗时 **138.125 秒**。配置解析并固定的请求模型是 **gpt-6-astra**，effort=low；这是请求模型名，不另行推测服务端内部路由。三次首次调用返回有效 search 计划，均使用“关联会话 → 事件锚点搜索 → 沿新发言者关联会话 → 事件锚点搜索”。三例四段必要原文均进入第二轮真实模型输入，同名第三账号的无关原文均未混入。

| 新案例 | 必要证据（fixture ID） | 首次规划耗时 | 最终调用进入 turn_wait | 最终调用结果 |
|---|---|---:|---:|---|
| 银湾烧制延期 | 7101 → 7102/7103 → 7104 | 17.844 s | 1.422 s | 25.063 s 超时 |
| 折纸题稿限定澄清 | 7201 → 7202/7203 → 7204 | 20.093 s | 1.140 s | 25.094 s 超时 |
| 北坡采声两天后撤回暂案 | 7301 → 7302/7303 → 7304 | 21.625 s | 1.094 s | 25.062 s 超时 |

“进入 turn_wait”从工作进程启动前的单调时钟标记计时；此时 SDK 已取得 turn 提交响应，但没有取得完整结果。三次超时均发生在 **SDK 消费远端 turn 结果的等待阶段**，不是 SQLite/工具检索、Python worker 启动、SDK 初始化、提交响应或返回结果后的事件时间校验。超时均只终止所属独占 Job。父层测得的 25 秒略有进程清理开销，未放宽 25 秒等待截止。

这组观测还不能区分 turn_wait 内部的服务排队、模型生成或传输等待，不能归因为“预算不足”，也不能声称这些超时已修复。第二轮原始 prompt 为 11,359 / 11,760 / 11,575 UTF-8 字节；首轮 SDK 报告输入约 18,644–19,875 tokens，提示最终上下文并不只等于业务 payload，但本轮未做额外计费对照实验，因此不对上下文开销和超时作因果断言。

三次有回执的完成调用共报告 **58,378 输入 + 837 输出 = 59,215 tokens**；三次超时的 usage 均为 null，真实总消耗未知，不能当作零，也不能把 59,215 当整个套件的精确总量。

最终三例都保留四段原文，返回 partial / insufficient / 空 claims，未用伪模型或预设答案补齐。因此：**跨群、跨人物、跨时间的证据获取链已在三个新案例中由真实模型驱动成立；完整 ACM 式推理及最终答案尚未通过。** unknown/relative/explicit 事件时间字段通过工程回归，但本次没有真实最终 claim，不能宣称其真实模型效果已验证。最大三个案例已用完，本轮停止，不继续调参、加预算或补跑。
