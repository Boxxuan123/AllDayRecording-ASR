# 同步重复开销优化（2026-09-27）

## 实现

1. 桌面、处理状态、人物、审核、知识、提醒、人物记忆和洞察的已核验纯查询使用 `reading()`，由 SQLite `query_only` 强制只读。命令中的纯读取阶段也使用只读事务。声纹重匹配先读取一致快照，在事务外计算，再于写事务中核对输入后提交；输入变化时拒绝旧计算。同步响应 DTO 校验移到提交后。
2. 手机回执只记录结果；批末在 `setCursor` 前统一清理。回执、投影、覆盖层清理和游标仍在一次事务内。清理用集合 SQL，减少逐操作查询；保留多资源回执、历史回执恢复和延迟投影语义。
3. 全量加载时，转写 JSON 解析一次并按会话分组。正常回执合并受影响的 utterance ID，仅刷新这些记录。并发到来的更新集合保留到下一次刷新；审核更新复用会话与转写对象。冲突、非转写变化、失效的并发快照仍有全量恢复路径。
4. SQL 同时检查资源就绪、依赖、冲突和本轮排除 ID，再按创建顺序 `LIMIT`。实际发送每批最多查询 32 条；添加创建时间索引，并去掉调度日志额外读取完整候选队列的操作。
5. 审核和人物响应增加可选内容版本。相同版本跳过本地写入；客户端重启后用落库内容比较。审核只写变化项、删除消失项；人物只写变化项。审核更新单独刷新审核数据，人物缓存更新不重建转写页面。旧服务未返回版本时仍可按内容去重。审核接口本轮仍返回完整快照，版本用于本地去重。
6. 手机同步事务内复用人物基本信息。人物缓存不跨事务、不用于一般人物编辑命令。后台样本任务按会话合并：已排队任务覆盖后续修改，运行中的任务首次被修改时推进 generation，防止旧结果发布。每条操作仍独立验证 ID、payload、revision、依赖和冲突。

## 验证

| 场景 | 实际结果 |
| --- | --- |
| 21 个会话、2,100 条转写 | JSON 解析 2,100 次，原逐会话方式为 44,100 次 |
| 1,200 条队列、前 700 条受依赖阻塞 | 只解析返回的 32 条，排除 ID 和排序正确 |
| 一批 32 条回执 | 清理一次，投影延迟到达后才移除覆盖层 |
| 在清理后、游标更新处注入错误 | 回执清理、投影和游标全部回滚 |
| 审核、人物版本不变，包括重建客户端实例 | 数据库行写入和界面通知均为零 |
| 32 条标注指向同一人物、同一会话 | 一次人物 SELECT，一次队列 UPDATE；32 个独立回执，重放结果不变 |
| 写事务占用期间调用查询 | 查询正常完成，不等待写锁 |
| 声纹重匹配计算期间并发修改输入 | 写入正常完成，过时计算被拒绝 |
